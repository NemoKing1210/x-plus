# Post filter — design

Date: 2026-11-12
Status: approved approach, written design pending builder check
Feature id: `filter`

## Intent

Users want to remove posts they do not want to see. The examples that started
this work: a flag or word in the author's display name or in the post text,
posts with or without images, and "many other" properties. The filter must be a
builder, not a fixed list of switches, and it must support AND / OR.

One level of logic is enough (owner's decision): a **rule** is a named list of
conditions combined with "all" or "any"; a post is hidden when **any** rule
matches (rules are OR-ed). There are no nested condition groups.

## Goals

- A separate **Filtering** tab in the settings dialog.
- Master switch, off by default; existing behaviour is unchanged until the
  user opts in.
- Rule builder: add / rename / enable / disable / delete / reorder rules.
- Conditions: field + operator + value; per-rule "all / any" mode.
- Fields: author display name, @handle, post text, language, media, attachments,
  post metadata (promoted, verified, repost).
- Text operators: contains, does not contain, whole word, not whole word,
  starts with, ends with, equals, does not equal, empty, not empty, regex,
  not regex.
- Presence operators for media / attachments / metadata, with enum values.
- Live filtering that hides the whole timeline cell **before paint**, survives
  X's DOM recycling, and cleans up on settings change / disable / navigation.
- Per-rule **Test** action that counts posts on the current page matching the
  draft rule and briefly outlines them.
- Safe persistence: rules are normalized on load / save / import; an incomplete
  or invalid rule can never hide everything.

## Non-goals

- Nested AND/OR groups (owner chose one level).
- Filtering the focal post on a `/…/status/…` page. Replies on that page are
  filtered; the post the user opened is not.
- Actions other than hiding: no highlight, blur, placeholder, or "N hidden"
  counter.
- Filtering user cells in sidebars, notifications, direct messages, or search
  user lists — only posts (`SEL.article`).
- Persistent per-post decisions: matching is live against the current DOM.
- Regex timeouts or sandboxing (JS regex cannot be interrupted). Pattern length
  is capped; a pathological pattern is the author's responsibility (documented).
- Separate hashtag / mention / cashtag fields (text matching covers them).
- A "reply" metadata flag: X has no stable, localized-independent test id for
  the "Replying to" line, so it is omitted rather than shipped brittle.
- Searching the text of a quoted post. Quote **presence** is an attachment
  condition; a quote's own text is not searched.
- Filtering text that X has not loaded: on a truncated long post only the DOM
  text is searchable.
- Indexing the custom tab in settings search (same as Backup / About).

## Anti-goals

- An empty or half-filled rule must never match every post.
- No flash of unfiltered posts (mark synchronously in the mutation callback).
- No change to X's scroll, virtualization, or navigation: hiding is a CSS
  `display:none` on the existing cell, nothing is removed from the DOM.
- No measurable cost when the feature is off or has no enabled rules.

## Constraints

- Vanilla ES modules, no frameworks, no TypeScript (AGENTS.md).
- Settings go through `core/schema.js`; `GM_getValue` / `GM_setValue` are never
  called directly. Imported backups must be unable to produce invalid state.
- `interface` is not modified beyond exporting two existing helpers (promoted
  detection and quote-card detection) for reuse; a separate feature owns the
  filter.
- Every user-facing string in all 8 locales; `scripts/check-i18n.mjs` must know
  the new namespace and the runtime-generated keys.
- UI through `el()`, `xp-` classes, `var(--xp-*)` tokens; works in light, dim,
  lights-out.
- X selectors live in `SEL` (`core/constants.js`) or at the top of the module
  that owns them.
- Build artifacts are regenerated by `npm run build`; never hand-edited.

## Approaches considered

1. **Separate `filter` feature with its own per-post watcher — chosen.**
   Mirrors the proven pattern in `interface/engine.js`: one `MutationObserver`,
   a dirty-article queue, synchronous marking before paint, marks taken back
   when X reuses nodes. The feature owns its settings, tab, styles and engine.
   Cost: a second observer on the same mutation stream and roughly 100 lines of
   observer/bookkeeping logic duplicated from `interface`.
2. **Extend `interface` with a dynamic rule — rejected.** One observer and no
   duplicated bookkeeping, but `interface` is built around static `RULES`, a
   master switch and boolean fields; user-authored rules blur its
   responsibility, overload its tab, and a bad user regex would sit inside the
   same engine as the whole clean-up.
3. **Check posts from the shared debounced `scan` hook — rejected.** 350 ms
   debounce plus a full-page walk means posts flash and scrolling janks.

Rule storage: **a new schema field type** (list of normalized record objects)
rather than a JSON string in a text field. The schema is the single source of
truth for load / save / import / reset; a text field would let a corrupt backup
put the script into an invalid state and would bypass reset semantics.

## Design

### Settings model

```js
filter: {
  enabled: false,
  rules: [
    {
      id: 'r-3f2a1c',            // stable UI key, generated when missing
      name: 'Crypto spam',
      enabled: true,
      match: 'all',              // 'all' | 'any'
      conditions: [
        { field: 'text',  op: 'contains', value: 'airdrop' },
        { field: 'media', op: 'hasNot',   value: 'any' },
      ],
    },
  ],
}
```

Limits: `rules` ≤ 50, `conditions` per rule ≤ 20, rule name ≤ 60 chars, text and
regex values ≤ 500 chars, id ≤ 40 chars (`[a-z0-9-]`).

### Schema extension

Add `field.records(fields, { max = 50, idKey = 'id', idPrefix = 'r', sanitizeItem } )`
to `core/schema.js`:

- default: `[]`;
- normalization: accept arrays only; normalize every item with
  `normalizeFields(fields, item)`; drop non-objects; cap at `max`;
- `sanitizeItem(item)` (optional) runs after normalization and may blank
  cross-field invalid values. The filter uses it to blank an operator that is
  not allowed for its field and an enum value that is not in its field's
  catalog, so stored or imported garbage becomes an **incomplete** condition
  instead of a surprisingly broad one;
- ids: keep a valid, unique id; regenerate a missing / invalid / duplicate id as
  `<prefix>-<base36 counter + random>` so items remain addressable by the UI;
- works nested inside `field.record`, so a rule contains a list of conditions;
- unknown keys inside items are dropped like everywhere else.

Add unit tests for: nested lists of records, garbage input, id preservation and
regeneration, caps, defaults being deep copies.

### Feature layout

```text
src/features/filter/
├── index.js      # registerFeature: fields, tab, apply + badge
├── config.js     # field / operator / value catalogs (one source of truth)
├── match.js      # PURE: compileRules(cfg) and matches(facts, compiled)
├── facts.js      # DOM → facts for one article (selectors at the top)
├── engine.js     # observer, dirty queue, marks, generated CSS, test preview
└── settings.js   # custom tab renderer (rule builder)
src/styles/filter.css
```

`match.js` has no DOM dependency, so all matching semantics are unit-tested with
plain objects.

### Condition catalog (`config.js`)

```js
FIELDS = {
  authorName: { ops: TEXT_OPS },
  handle:     { ops: TEXT_OPS, value: 'handle' },
  text:       { ops: TEXT_OPS },
  lang:       { ops: ['is', 'isNot'], value: 'lang' },
  media:      { ops: ['has', 'hasNot'], value: ['any', 'photo', 'video'] },
  attachment: { ops: ['has', 'hasNot'], value: ['link', 'quote', 'poll', 'article'] },
  meta:       { ops: ['is', 'isNot'], value: ['promoted', 'verified', 'context'] },
}

TEXT_OPS = [
  'contains', 'notContains', 'word', 'notWord', 'startsWith', 'endsWith',
  'equals', 'notEquals', 'empty', 'notEmpty', 'regex', 'notRegex',
]
```

The same catalog drives: normalization (via `sanitizeItem`), the settings UI
(field select → allowed operators → value control), the matcher, and the i18n
dynamic-key check. `empty` / `notEmpty` take no value.

**Grammar of `op` and `value` in storage:** both are plain `field.text('')`,
not enums, because their valid set depends on `field`. An operator that is not
in the field's list, or an enum value not in the field's catalog, is blanked by
`sanitizeItem`; a blank / invalid pair makes the condition **incomplete** and
therefore ignored. This is deliberate: coercing garbage to a valid `not…`
operator would turn one bad value into "hide everything".

**Language values:** the UI is a text input with a `datalist` of the
`TARGET_LANGUAGES` codes plus free-form entry, because that list is a
translation-target list and does not cover every `lang` value X emits. Values
are normalized to lower case. `is` matches a post whose `lang` equals the value
or starts with `value + '-'` (so `en` matches `en-GB`; `zh-CN` does not match
bare `zh`). `isNot` is the negation of that match, and both are false when the
post has no `lang` attribute — unknown is not treated as "not English".

**Media values:** `any`, `photo`, `video`. GIFs count as video: X serves them as
`<video>` and the DOM does not reliably distinguish them.

**Metadata values:** `promoted`, `verified`, `context`.

- `promoted` reuses `isPromotedArticle` from `interface/rules.js`, exported for
  this purpose.
- `verified` looks at `[data-testid="icon-verified"]` **inside the outer
  author's header only**, so a verified account quoted in the post does not
  make the outer post "verified". Quote-card headers are excluded with the same
  quote-card detection used for text.
- `context` means the post's cell carries `[data-testid="socialContext"]`. X
  uses that row for "reposted", "pinned" and "liked by", so the condition is
  deliberately named and labelled as a context line rather than a repost flag;
  localizing the text to isolate reposts would be brittle. A precise repost
  flag is a non-goal.

### Matching semantics (`match.js`)

Facts object for one post:

```js
{
  authorName: 'Display Name 🇺🇦',
  handle: 'user',                      // normalized, no @
  text: 'post text as in the DOM',
  lang: 'en',                          // lower-case, '' when unknown
  media: Set(['photo' | 'video']),
  attachments: Set(['link' | 'quote' | 'poll' | 'article']),
  meta: Set(['promoted' | 'verified' | 'repost']),
}
```

Rules:

- A condition is **complete** when its field is known, its operator is allowed
  for that field, and (for operators that take a value) the value is non-empty
  and, for enum-valued fields, present in the field's catalog. An incomplete
  condition is ignored (not false) so a half-typed new condition does not
  change the result; a rule with zero complete conditions never matches. This
  is the last line of defence behind `sanitizeItem`.
- Text comparison is Unicode-aware and case-insensitive. Whole-word matching
  wraps the escaped value in Unicode letter/digit boundaries
  (`(?<![\p{L}\p{N}_])…(?![\p{L}\p{N}_])`). Values are matched against the
  lower-cased fact; `handle` values are normalized with `normalizeHandle`.
- `lang`: see the catalog rules above — exact or `value + '-'` prefix; both
  operators are false when the post's language is unknown.
- `media` / `attachment` / `meta`: `has` checks the set; `hasNot` is its
  negation; `any` means "the set is non-empty".
- `regex`: `/pattern/flags` form is honoured; otherwise compiled with `iu`.
  Compilation happens once per settings change. An invalid pattern makes that
  condition never match and is surfaced in the UI; it never throws into the
  page.
- Rule result = `all` / `any` over complete conditions. Post result = any
  enabled rule matches, and the master switch is on.

### DOM facts (`facts.js`)

Selectors at the top of the module (following DEVELOPMENT.md); the ones that
already exist in `SEL` are used from there.

- Scope: `SEL.cell` elements that contain an `SEL.article` inside
  `SEL.primaryColumn`. Skip articles inside `[role="dialog"]` and our own UI.
  On a `/…/status/…` path, the first article in the primary column is the focal
  post and is never filtered.
- Own text: the first `SEL.tweetText` that is not inside a quote card. Quote
  cards are detected with the same approach as `interface/rules.js`
  (`SEL.quoteTweet`, or a `role="link"` block holding `SEL.quoteAvatar`).
- **Emoji-aware, read-only text.** X renders emoji (including flag emoji) as
  Twemoji `<img alt="…">` or `[role="img"][aria-label]`; `textContent` omits
  them, which would break the motivating "flag in the name" case. `facts.js`
  uses its own `plainText(root)` tree walk that concatenates text nodes and
  substitutes each emoji image's `alt` / `aria-label`. It must **not** reuse
  `materializeEmojiImages()` from `utils/linked-text.js`, because that helper
  *replaces* nodes in X's live DOM; filtering is read-only. The walker is a few
  dozen lines and needs no clone.
- Display name: first anchor in `SEL.userName` whose text does not start with
  `@`, read with `plainText`; fallback to the header's first text block.
- Handle: the `@…` anchor in `SEL.userName`, normalized with `normalizeHandle`.
- Language: the `lang` attribute of the outer `SEL.tweetText`.
- Media: `SEL.photo` → `photo`, `SEL.videoPlayer` / `[data-testid=
  "previewInterstitial"]` → `video`.
- Attachments: `[data-testid="card.wrapper"]` → link, `[data-testid=
  "card.poll"]` → poll, quote card → quote, `[data-testid="article-cover-
  image"]` → article. Poll test id is the one thing to verify against today's X
  and the harness.
- Metadata: promoted via `isPromotedArticle`; verified via
  `[data-testid="icon-verified"]` scoped to the outer author's header; context
  via `[data-testid="socialContext"]` in the closest cell (see the catalog
  notes for the exact meaning of each).
- Facts are extracted once per processed article (not cached across passes,
  because X mutates posts in place).

Working within one article also means the quoted post's text, media and avatar
are not mistaken for the outer post's: quote cards are excluded per fact.

### Engine (`engine.js`)

Modeled on `interface/engine.js`:

- `sync(cfg)` from `apply`: compile rules; write the stylesheet
  (`[data-xp-filtered]:not([data-xp-peek]){display:none!important}`, the
  `:not` lets the Test preview reveal a hidden post — the same trick
  `interface` uses); connect or disconnect the observer; reprocess every
  article on screen; take back all marks when the feature or all rules are off.
- One `MutationObserver` on `document.documentElement` (`childList`, `subtree`).
  Added / changed nodes inside an article enqueue that article; added subtrees
  enqueue the articles they contain. Duplicate work is collapsed in a `Set`.
- Processing runs synchronously in the mutation callback (before paint) within
  an 8 ms budget, then continues on `requestAnimationFrame`; same pattern as
  `interface` (its `BUDGET_MS`).
- Marking: `target = article.closest(SEL.cell) || article`; a match sets
  `data-xp-filtered` on the cell. A `WeakMap<article, cell>` remembers what was
  marked so a stale mark is removed when the post stops matching, when X
  recycles the cell, or when rules change. On navigation, a sweep clears marks
  from cells that no longer contain an article.
- Idempotent: processing the same post twice produces the same marks.
- No layout reads and no `getComputedStyle`; decisions come only from the DOM
  facts.
- Settings test preview: `previewRule(draftRule)` compiles **the draft rule**
  (not the saved config), sets `data-xp-peek` on every matching cell and
  article so the live filter's `display:none` is lifted and the match becomes
  visible, then outlines it with a dedicated style element. Because a saved
  rule may already have hidden the post, revealing is part of the preview, not
  an afterthought. It returns the number of matching posts **currently visible
  on screen** (the `interface` peek convention), so `peek.missing` appears only
  when the current viewport has no matches even though the page might.
  Teardown needs no hook: the settings renderer's `endPeek()` removes every
  `data-xp-peek` attribute on close, and the filter stylesheet hides those
  cells again. The custom tab toggles the backdrop's `is-peeking` class for
  translucency.

### Settings tab (`settings.js`)

Custom `render(ctx)` tab (the spec renderer cannot express a dynamic nested
list). Built from the existing controls (`createSwitch`, `createSelect`,
`createTextInput`, `createButton`, `createHint`, `createSection`) plus
filter-specific markup and `src/styles/filter.css`.

- Master switch + short explanation ("rules are combined with OR").
- Empty state with an "Add rule" button.
- Rule card, top to bottom:
  - header: enable checkbox, name input, Move up / Move down, Delete;
  - mode select: "All conditions" / "Any condition";
  - condition rows: field select, operator select (options depend on the
    field), value control (text input, language input with a `datalist` of the
    known codes, enum select, or nothing for `empty` / `notEmpty`), Remove;
  - inline warning for an invalid regex; a muted hint for an incomplete
    condition;
  - "Add condition" (disabled at 20) and "Test" buttons. Test previews the
    draft rule, reveals posts the saved filter had hidden, outlines them and
    reports how many are on screen.
- "Add rule" disabled at 50 with a hint.
- Edits replace arrays/objects in the draft and repaint the rule list locally;
  `ctx.changed()` keeps the tab badge and the dialog state in sync. Nothing is
  saved or applied until **Save**, like every other tab.
- Tab badge: number of enabled rules, or the common "off" label when the master
  switch is off (mirrors `interface`).

### i18n

- New namespace `filter` added to `NAMESPACES` in `scripts/check-i18n.mjs`.
- `dynamicKeys()` imports `features/filter/config.js` and adds

- Static keys: title, master switch + hint, section title/description, rule
  builder labels, buttons, limits, empty state, invalid regex, test result

- Add every key to `en`, `ru`, `zh`, `es`, `pt`, `de`, `fr`, `ja`.

## Decisions made in conversation (owner delegated "the best and most reliable")

- Separate feature instead of extending `interface`.
- One level of conditions, no nesting.
- Default off; a new rule defaults to "all conditions".
- Media: `any` / `photo` / `video`; GIFs counted as video.
- Metadata: promoted / verified / repost; no reply flag.
- The focal post on a status page is never hidden.
- Test button with a count and a temporary outline instead of a live preview.
- Rules are OR-ed; a post is hidden on the first matching rule.
- Limits and caps above.

## Builder-check resolutions (my calls)

A fresh reviewer read this document and raised five gaps. Each is settled above
and recorded here so the owner can veto the call while reading:

1. **Emoji in names / text:** yes, facts use an emoji-aware `plainText()` walk
   (`img[alt]`, `[role="img"][aria-label]`), without touching X's DOM.
2. **Unknown operator / enum value:** `field.records` gains a `sanitizeItem`
   hook; the filter blanks cross-field invalid pairs, and the matcher treats
   them as incomplete. A bad imported rule can never become "hide everything".
3. **Metadata scoping:** `verified` is the outer author only; the old `repost`
   value is renamed `context` and documented as X's social-context line
   (reposted / pinned / liked by), because a precise repost flag would need
   brittle localized detection.
4. **Language vocabulary:** free-form input with `TARGET_LANGUAGES` as
   suggestions; `is` = exact or `value + '-'` prefix, `isNot` = its negation,
   both false when the language is unknown.
5. **Test with already-hidden posts:** the filter CSS excludes
   `[data-xp-peek]`, so Test reveals matches before outlining them; the count is
   the matching posts visible on screen.

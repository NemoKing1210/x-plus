# Post screenshot — design

Date: 2026-11-15
Status: approach chosen, awaiting owner approval
Feature id: `screenshot`

## Intent

A user reading a post wants to share it as an image without taking a manual
screen region capture or assembling it in an editor. One click on a control next
to **Translate** should put a PNG of the post — as it appears on the page — into
the clipboard, ready to paste into a chat or an editor. The feature is **off by
default**.

Owner's words for the content: "the post as it looks" — current X theme,
author header, post text (translated text included when translation is
displayed), media, quote card, poll, action row. Only our own injected chrome is
removed from the image.

## Goals

- A separate `screenshot` feature with its own master switch, **off by default**.
- One button per post article, in the header actions row, immediately after the
  Translate button when that feature is on, and in the same row (before
  Grok / ⋮) when Translate is off. A quoted post needs no button of its own:
  it is part of the outer image.
- One click → PNG of the post element in the clipboard.
- Faithful rendering: computed colours, fonts, images, emoji, rounded media,
  quote card, polls, action row.
- Visible feedback: spinner/label while working, success toast, warning toast
  when the image had to be saved instead of copied, error toast on failure.
- Fallback: when the clipboard cannot accept an image, download the PNG.
- Zero cost when disabled: no observers, no per-scan DOM work.

## Non-goals

- X Articles (long-form) and non-post surfaces (user cells, DMs, notifications).
- Animated video / GIF output: a video is captured as its poster image (or a
  neutral placeholder when X exposes no poster).
- Auto-expanding "Show more": the post is captured as it is displayed.
- Screenshot history, preview dialog, editing, or re-copy.
- A filename template or a format choice: the file is always PNG (the clipboard
  needs PNG), named `x-plus-post-<handle>-<id>.png`.
- Firefox image clipboard: Firefox has no `ClipboardItem` image write; it gets
  the download fallback.
- Capturing hover states, tooltips, menus, or content outside the post element.
- Adding a screenshot entry to the post ⋮ menu (can be added later).

## Anti-goals

- Never mutate the live post for capture: work on the library's clone.
- Never capture our own UI (button, translate panel/toolbar).
- No change to X's scrolling, virtualization, navigation, or the post click.
- No regression in Translate placement or its teardown when the two features
  are enabled/disabled independently.
- No canvas taint: all images must be embedded, not drawn from live
  cross-origin nodes.

## Constraints

- Vanilla ES modules, no frameworks, no TypeScript (AGENTS.md).
- One small runtime dependency is accepted **by owner decision**:
  `modern-screenshot` (4.7.x, ~20 KB min+gzip bundled). It was chosen over a
  hand-written renderer specifically for reliability.
- Settings go through `core/schema.js`; no direct `GM_getValue` / `GM_setValue`.
- Every user-facing string in all 8 locales; `scripts/check-i18n.mjs` must know
  the new namespace.
- UI through `el()` / `xp-` classes / `var(--xp-*)`; works in light, dim and
  lights-out.
- X selectors live in `SEL` (`core/constants.js`) or at the top of the owning
  module.
- Build artifacts are regenerated by `npm run build`; never hand-edited.
- Clipboard write needs a user gesture, so the write is started synchronously in
  the click handler with a `Promise<Blob>`.

## Approaches considered

1. **Own DOM → SVG `foreignObject` → canvas pipeline — rejected.** No
   dependency, full control, and only one post to render. But we would own the
   fragile parts: computed-style inlining, `@font-face` embedding, pseudo
   elements, image placeholders, Safari/Firefox decode fixes. The owner asked
   for the most reliable option, not the leanest.
2. **Bundle `modern-screenshot` and adapt it to X — chosen.** It is the same
   `foreignObject` technique, already hardened: computed styles, font embedding,
   image embedding with progress/timeout, `filter` for excluding nodes,
   `onCloneEachNode` for X-specific replacements, `fetchFn` as a CORS/CSP escape
   hatch, and `maximumCanvasSize` guards. X's CDNs send
   `access-control-allow-origin: *` (`pbs.twimg.com`, `abs.twimg.com`) and
   `x.com`'s CSP allows `data:`/`blob:` images and `https://*.twimg.com`
   connections, so the library's default fetch path works; `fetchFn` stays a
   fallback we can wire to `GM_xmlhttpRequest` if a manager or a future CSP
   breaks it.
3. **Re-render the post from extracted data on a canvas — rejected.** Robust
   and dependency-free, but it would not be "the post as it looks": every
   layout, colour and font decision would have to be re-implemented and would
   drift from X.

## Design

### Settings model

```js
screenshot: {
  enabled: false, // off by default
  background: 'theme', // theme | white | black | transparent | custom
  customBackground: '#000000', // used by 'custom', any CSS color
  scale: 'auto', // auto | 1 | 2 | 3
  actions: true, // keep the reply/repost/like/views row
  save: false, // save the PNG instead of copying it
}
```

A spec tab, not a custom renderer:

- `screenshot.title` (`Screenshot`), badge `common.off` while disabled.
- **Screenshot** section: the master switch (`screenshot.enabled`) and
  `screenshot.save`.
- **Appearance** section (when enabled): background select, the custom color
  field (only for `custom`), and the scale select.
- **Content** section (when enabled): keep/trim the action row.
- No other controls.

The default `theme` background is always opaque: it takes the first painted
page color, otherwise the detected theme's color (`#ffffff`, `#15202b` or
`#000000`). `transparent` is the only mode that produces a transparent PNG.

### Feature layout

```text
src/features/screenshot/
├── index.js       # registerFeature: fields, tab, apply / scan / navigate
├── config.js      # ss() scoped t(), SC_ATTR markers, limits
├── button.js      # create / place / label / loading state, remove-all
├── capture.js     # clone preparation + domToBlob options
├── background.js  # pure background color parsing / fallbacks
└── copy.js        # ClipboardItem → clipboard → download fallback → toasts
```

`src/ui/icons.js` gains a `camera` glyph. No new stylesheet: the control reuses
`.xp-btn`, `.xp-btn--header`, `.xp-btn__spinner`, `.xp-btn__icon` and
`.xp-header-action` from `styles/translate.css`, which is always imported.

### Placement and lifecycle

- Reuse the proven header-slot logic instead of duplicating it: export
  `findHeaderActionsSlot` from `features/translate/placement.js` (it already
  handles the structural fallback when X renames atomic row classes) and reuse
  `mountHeaderButton` with the quote flag `false`. The quote-header branch of
  the slot finder cannot trigger here: it is keyed on `getQuoteCard(article)`,
  which returns `null` for a whole post article. This mirrors how `filter`
  reuses `interface/rules.js` exports.
- Button marker is `data-xp-shot-btn`, deliberately different from Translate's
  `data-xp-btn`, so `getTranslateButton()` never picks it up.
- The wrapper carries `xp-header-action` (shared styling) plus
  `data-xp-shot-action` for identification.
- Ordering: after mounting, if the row contains a Translate wrap, move ours
  directly after it. When Translate is off there is no wrap and the button
  stays where `mountHeaderButton` put it (before Grok / ⋮).
- Translate's `teardownAllPosts()` currently removes every `.xp-header-action`
  on the page, which would also delete our wrapper when Translate is disabled.
  Change that sweep to remove only wraps that contain `[data-xp-btn]` or are
  empty. This is behaviour-preserving for Translate and removes the
  cross-feature conflict. Our own `removeAllButtons()` removes every
  `[data-xp-shot-action]` and any wrapper left empty.
- `scan()`: return immediately when disabled; otherwise walk **top-level**
  `SEL.article` elements (skip anything inside `[data-xp-ui]` or inside another
  `SEL.article`), and ensure one button per article. If X re-renders the header,
  the next debounced scan re-mounts it. If `findHeaderActionsSlot` finds no slot
  (X markup changed / no Grok, caret or header row), the button is simply
  omitted for that post and retried on the next scan; we do **not** borrow
  Translate's toolbar, which is its own UI and is stripped from captures. Cost
  is two cheap queries per article on scans that already walk the page; zero
  when off.
- `apply(cfg)`: disabled → remove all; enabled → `scanPosts()`. `navigate()` →
  `scanPosts()`. No observers of our own.
- Click is handled in the capture phase with `preventDefault` /
  `stopPropagation` (and `silencePointerEvents`) so the post does not open.

### Capture pipeline (`capture.js`)

`capturePost(article)` → `domToBlob(article, options)`.

- `scale`: the `scale` setting; `auto` = `clamp(devicePixelRatio, 2, 3)` — at
  least 2× for legible text, at most 3× to bound the canvas.
- `maximumCanvasSize`: 16384; `timeout`: 15000 ms.
- `backgroundColor`: `theme` (the default) walks `<body>`, `<html>` and the
  article's ancestors for the first opaque color and falls back to the theme
  color, so the image is never accidentally transparent. White, black, an
  explicit transparent PNG and a custom CSS color are settings; an invalid
  custom color falls back to the theme.
- `actions: false` filters out the post's own action row and passes an explicit
  capture height equal to the row's top edge, so the image ends where the
  content ends instead of leaving a blank strip.
- `save: true` skips the clipboard: the PNG is downloaded after the capture.
- `filter`: drop `[data-xp-ui]` (and therefore the translate panel, toolbar and
  our button). Everything X renders inside the article stays, including the
  Grok / caret controls, the action row and a quote card.
- Translation visibility follows the display mode: in `replace` / `split` the
  translated text is inside `tweetText` and is captured; in `panel` the
  translation is our UI and is **not** captured, so the image shows the original
  text. A user who wants the translation in the image switches display mode to
  replace. The live post is never mutated for capture.
- Videos: the library renders a video by seeking it and waiting for `seeked`,
  which never fires without a source, so a video **without a poster is filtered
  out** of the clone; its player container keeps a sized neutral block. Videos
  with a poster are rendered by the library from that poster (GIFs are videos
  on X and follow the same rule).
- The whole render is raced against `CAPTURE_TIMEOUT_MS`, so a renderer that
  never settles still ends in the error toast instead of leaving the button
  disabled forever.
- `font`: leave the default embedding on (X's font files are CORS-enabled).
- `fetchFn`: not wired in v1; the default fetch path is sufficient. If a real
  environment blocks it, `fetchFn` can return a data URL loaded through
  `core/http.js` (`gmRequest`), returning `false` to fall back.
- `features.restoreScrollPosition`: false (the post itself is not scrolled).
- `progress`: drives nothing in v1; the button spinner is enough.

The capture is started directly in the click handler and its promise is handed
to the clipboard, so no `await` sits between the gesture and the write.

### Clipboard, fallback and feedback (`copy.js`)

```js
const blobPromise = capturePost(article);           // started synchronously
const item = new ClipboardItem({ 'image/png': blobPromise });
await navigator.clipboard.write([item]);            // consumes the gesture
```

- Success → success toast; button returns to idle.
- No `ClipboardItem` / `clipboard.write` (Firefox, insecure context) or a
  rejected write → await the blob, `saveBlob()` it as
  `x-plus-post-<handle>-<id>.png`, warning toast ("couldn't copy, saved the
  file"). Handle a rejected `blobPromise` once so no unhandled rejection leaks.
- Capture failure → error toast + `logWarn(Codes.SCREENSHOT_FAILED, …)`.
- Button: `setButtonLabel(btn, ss('copying'), { loading: true })` while working;
  ignore re-clicks while loading; restore the idle label afterwards.
- No layout shifts: the label is short in every locale ("Copy", "Копировать"…),
  same as Translate's header button.

`saveBlob` currently lives in `features/media/download.js`. Move it to
`src/utils/download.js` and re-export from the media module (or import it from
there) so `screenshot` does not depend on the media feature.

### Errors

Add `SCREENSHOT_FAILED: 'XP-1501'` to `core/debug.js`. Capture and clipboard
failures are logged once with details; user-visible failures also toast.

### i18n

- New namespace `screenshot` in `NAMESPACES` (`scripts/check-i18n.mjs`).
- Add a scoped pattern like the existing `tr()` / `tm()` ones:
  `/ss\(\s*'([\w.]+)'/g` → `screenshot.`.
- Keys: `title`, `sectionMain`, `sectionMainDesc`, `enabled`, `enabledHint`,
  `button`, `copying`, `copied`, `saved`, `captureFailed`.
- Add every key to `en`, `ru`, `zh`, `es`, `pt`, `de`, `fr`, `ja`.

### Verification

- `npm run ci` (syntax + i18n + tests + build + artifact verification).
- Harness (`npm run build && npm run harness`): enable the feature, check the
  button mounts next to Translate; disable Translate and confirm the screenshot
  button survives and re-mounts after a rescan; quote post and video post
  render.
- Real X in a userscript manager, per `docs/DEVELOPMENT.md`: copy a text post, a
  photo post, a video post, a quote post and a poll; paste into an image editor
  and compare with the screen in light, dim and lights-out. Check a translated
  post in replace mode (translation in the image) and in panel mode (original
  text in the image).
- Confirm the feature is off after a fresh install and that no button appears.

## Decisions made in conversation (owner delegated "the best and most reliable")

- Content: the post as it looks, not a clean re-rendered card.
- Approach: the battle-tested library, not a hand-written renderer, for
  reliability; size is accepted.
- Master switch off by default.
- The screenshot button is its own feature and works independently of
  Translate.
- One button per post, including a post that quotes another; the quote is part
  of the captured image.

## Builder-check resolutions (my calls)

A fresh reviewer read this document and raised three gaps. Each is settled
above and recorded here so the owner can veto the call while reading:

1. **Quote posts:** the scan unit is the top-level article, not the translate
   feature's per-text-root unit. One button in the outer header; the quote card
   is captured with the rest of the post. `mountHeaderButton` gets
   `inQuote = false`.
2. **Panel-mode translation:** our panel/toolbar is `[data-xp-ui]` and is
   stripped, so the image shows the original text in panel mode and the
   translated text in replace/split mode. No special-case that would mutate the
   live post.
3. **No header slot:** omit the button for that post and retry on the next
   scan. Do not reuse Translate's toolbar, which is translate-owned UI and would
   be stripped from the capture anyway.
